GenICam Capture Recipe

GenICam カメラの設定・撮影手順・撮影データを、ベンダーや機種に依存せず共有するためのファイル形式と、その Python (Harvesters) 参照実装です。

日付 2026-10-16 リポジトリ dotchang/genicam-format-prototype 検証環境 Windows 11 · Python 3.13 · harvesters 1.4.3 · genicam 1.6.0

背景と目的

撮影条件は、ベンダーツールの設定ファイル (.pfs など) や GenApi の永続化ファイルに保存されるのが普通です。これらは機種のノード構成に紐づいているので、論文や OSS で第三者に渡しても、別の機種では読めません。さらに「設定したつもりの値」と「カメラが実際に受け入れた値」(露光時間の量子化、範囲外のクランプなど) の差は、どこにも残りません。

GCR は次の 3 点を満たすことを目標にしました。

  • ベンダー非依存: ノード名は GenICam SFNC の名前を共通語彙にし、機種差はプロファイルで吸収する。
  • 人が読める: 手で書く文書は YAML で、設定は 1 行 1 項目。
  • 機械検証できる: JSON Schema、適用結果の読み戻し記録、SHA-256 マニフェストを持つ。

4 つの文書

*.profile.yaml

Profile

機種プロファイル。SFNC 名から機種固有ノードへの別名と、線形の値変換 (例: GainRaw → dB)。

*.config.yaml

Config

カメラ設定。順序付きリストで、各項目に必須度・許容誤差・単位・セレクタを持つ。

*.recipe.yaml

Recipe

撮影手順。Config を参照し、トリガ方式・枚数・チャンク・保存形式を書く。

bundle/

Capture Bundle

撮影結果。画像、適用結果、全ノードの読み戻し、デバイス情報、GenICam XML 原本、ハッシュ。

Config の書き方

設定は上から順に適用され、1 項目ずつ読み戻して判定されます。順序は意味を持ちます (自動露光を切ってから露光時間、幅を決めてからオフセット)。

gcr_version: "1.0"
kind: config
name: low-noise-mono
target: { pixel_format_family: mono, min_bit_depth: 12 }
settings:
  - { node: PixelFormat, value: [Mono12, Mono12p, Mono16] }   # 候補リスト: 先頭から使えるもの
  - { node: Width, value: "@max" }
  - { node: OffsetX, value: "@center", level: preferred }
  - { node: ExposureAuto, value: "Off" }
  - { node: ExposureTime, value: 10, unit: ms, tolerance: 1% } # ms → us は自動換算
  - { node: Gain, selector: { GainSelector: All }, value: 0.0, unit: dB, level: preferred }
  - { node: Gamma, value: 1.0, level: optional }
  • 候補リスト: Mono12 が無い機種でも Mono12p や Mono16 で再現できる。
  • 特殊値: @max / @min / @center はデバイス上の範囲で解決する。
  • 単位: s ms us ns Hz kHz MHz dB を換算。デバイスが単位を宣言しないときは SFNC の既定単位を使う。
  • 許容誤差: 絶対値か "1%"。省略時は整数が 1 刻み未満、浮動小数が 0.1%。

必須度と判定

各設定の level は、再現できなかったときの扱いを決めます。required が 1 つでも failed になると撮影は中止されます (--force で続行)。

ノードが無い・書けない・候補が全滅failedskippedskipped

この判定結果がそのまま Bundle の applied.json に残るので、別の機種で同じ Recipe を使ったときに「どこが一致しなかったか」を後から説明できます。

gcr verify はファイルの欠落・改変・未登録を検出します。gcr diff recipe bundle は「意図した設定」と「実際の読み戻し」を比較します。

テストの内容

  • 単体テスト (FakeNodeMap): 適用順、量子化された露光の許容誤差判定、候補リスト、@max/@center と刻み合わせ、セレクタ、クランプ、読み取り専用ノード、コマンド実行、プロファイルの別名と変換、プロファイル照合、単位換算。
  • フォーマット: サンプルとプロファイル全件をモデルとコミット済み JSON Schema の両方で検証。スキーマがモデルと一致していること。不正文書 (タイプミスのフィールド、value と execute の併用など) の拒否。
  • 撮影 (FakeCamera): ソフトウェアトリガ撮影、ウォームアップ破棄、frames.csv とチャンク、改ざん検出、required 失敗時の中止と --force。
  • シミュレータ結合: Viky で dump → validate → apply → capture → verify → diff を一周。

実装中に見つかった問題

相対パスの .cti ではカメラが 0 台になる

Harvesters に相対パスの viky.cti を渡すとエラーなしで 0 台になりました。絶対パスでは 3 台見つかります。gcr は .cti のパスを常に絶対パスに変換します。

genapi の is_feature / is_selector はメソッド

属性として真偽判定すると常に真になり、内部ノード (*_Val など) がスナップショットに混ざり、全ノードがセレクタ扱いになっていました。呼び出して判定するよう修正し、結合テストで内部ノードが出ないことを確認しています。

単位換算の丸め誤差

1e-3 / 1e-6 は 1000 ちょうどにならず、2 ms が 2000.0000000000002 us になりました。単位表を 10 の指数で持つように変更しました。

制限と今後

  • 検証はシミュレータのみです。実機プロファイルは viky (検証済み) と basler-ace-gige-legacy (未検証の例) の 2 件だけです。
  • マルチコンポーネント (GenDC・3D) は先頭コンポーネントのみ保存します。
  • 単位換算は時間・周波数・dB のみ、セレクタ展開は enum セレクタ 1 段のみです。
  • ライセンスは未設定です。OSS として公開するにはライセンスの決定が必要です。
  • 次の段階: 実機 2 機種以上で同じ Recipe を撮り、gcr diff の結果が説明可能かを確認する。
